Repository memory (the Manifold)

#
docsmanifoldD-007

Each kind of project knowledge has one owning document, and a checker keeps them consistent.

What it does

The project's state, rules, plan, decisions, tests, and security notes live in a small set of Markdown documents, each with one owner and an update trigger. python3 tools/check_docs.py fails when they disagree: a missing roadmap or decision ID, a broken link, or a path in the repository map that does not exist.

How it works

  1. AGENTS.md holds the standing rules and the repository map; CLAUDE.md only imports it.
  2. ROADMAP.md keeps permanent item IDs, docs/DECISIONS.md keeps accepted choices with their alternatives, and docs/HANDOFF.md is rewritten each time the current state changes.
  3. docs/README.md lists which document owns which fact and what change should trigger an update.

Why it works this way

Recorded in D-007: a fresh agent session starts with no memory, so the repository has to carry it, and a checker is the cheapest way to stop the documents from quietly contradicting each other.

  • Agent rules and map AGENTS.md
  • Who owns what docs/README.md
  • The checker tools/check_docs.py

This manual (the 3x scheme)

#
docs3xD-007

A JSON source builds one standalone HTML manual with a What, a How, and a Why for each topic.

What it does

The manual you are reading is generated from docs/plainchant-scribe.manual.json. Each entry states what something is, how it works, and why it is that way, and cites repository evidence. The generator refuses invalid or placeholder-filled sources.

How it works

  1. tools/manual.py check validates the source against docs/manual.schema.json.
  2. tools/manual.py build writes docs/manual.html, which is committed.
  3. tools/test_manual.py tests the generator and checks that this manual builds.

Why it works this way

Recorded in D-007: the Markdown documents are precise but scattered, and a single explorable synthesis helps a newcomer see the shape before reading the details, at the cost of one more document to keep true.

Evidence
  • Manual source docs/plainchant-scribe.manual.json
  • Generator tools/manual.py
  • Schema docs/manual.schema.json
  • Generator tests tools/test_manual.py

Where the code comes from

#
historyD-003

Scribe is a spinoff of Plainchant Web; a digest carries the history that still matters.

What it does

Plainchant Scribe started from a copy of Plainchant Web's source at one named commit, without its git history. A digest records what that project built, which of its decisions still apply to Scribe, and the mistakes that cost it time.

How it works

  1. The copy was made at roadmap item P0-02 with git archive from the commit hash recorded in D-003, then renamed at P0-03.
  2. docs/archive/plainchant-web-lineage.md lists the decisions as keep, adapt, or drop, and the gotchas, using a numbering form the documentation checker ignores.
  3. The upstream repository stays the place for full history.

Why it works this way

Recorded in D-003: a long inherited history would flood a new session's context with features Scribe removes, while a digest keeps the lessons.

Evidence
  • The digest docs/archive/plainchant-web-lineage.md
  • The decision docs/DECISIONS.md

The manuscript look

#
designthemeD-008

One palette of paper and ink in a light and a dark mode, with serif headings and typewriter code.

What it does

The studio and the home page share a warm paper-and-ink look. Settings offers Match system (the default), Light, and Dark. Headings use EB Garamond, code uses Courier Prime, and dense controls use Inter. The Stage still shows your book on white paper, because the book's own styles decide how it looks.

How it works

  1. src/styles.css defines every colour and shadow as a CSS variable. :root is the light palette; the dark palette is written once for the system setting and once for the manual choice, so the page has no flash on load.
  2. src/app/settings.js applies the choice as data-theme on the root element and sets the browser's theme colour.
  3. test/theme.test.js checks that every text, button, and syntax-colour pair reaches 4.5:1 contrast in both modes, that the two dark blocks match, that no colour is hard-coded outside the theme blocks, and that the home page uses the same palette.

Why it works this way

Recorded in D-008: a book tool is about written pages rather than code, so it gets its own look instead of the inherited dark developer chrome, at the cost of keeping two palettes checked.

Evidence
  • Palettes and type src/styles.css
  • Theme setting src/app/settings.js
  • Home page style src/home.css
  • Contrast and parity tests test/theme.test.js
  • EB Garamond licence fonts/OFL-EBGaramond.txt

The plan in brief

#
roadmapepubD-002

An EPUB studio whose book files stay the source of truth, built in eight phases.

What it does

Plainchant Scribe lets an author make, lay out, check, and export reflowable EPUB 3.3 books. The book's XHTML, CSS, and package files are authoritative and are edited by exact-range splices, never rewritten. Phases 0 to 4 and most of Phase 5 are built; ROADMAP.md says which items are left.

How it works

  1. ROADMAP.md orders the work: spinoff and renaming, the XML and book format, the Reading Stage, structure tools, layout, import and export with validation, accessibility, and later extras.
  2. Validation is a built-in rule set plus an optional EPUBCheck run in the desktop app (D-005).
  3. Markdown is import only, and Kindle formats are out of scope (D-002, D-006).

Why it works this way

Recorded in D-002 and D-004: keeping the author's files untouched is the idea that made Plainchant Web trustworthy, and a reflowable EPUB 3.3 target serves most authors with the least moving parts.

Evidence
  • The roadmap ROADMAP.md
  • The decisions docs/DECISIONS.md
  • Planned architecture docs/ARCHITECTURE.md
