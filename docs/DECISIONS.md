# Decisions

Short, append-only record of choices that a future session might otherwise re-litigate. One entry per decision.
Newest at the bottom. To reverse a decision, add a new entry that supersedes it; the old one keeps its text and only
its status changes ("superseded by D-MMM"). An "Update, same session" note at the end of an entry is fine while it is
still on the working branch.

Record pre-existing choices too, the first time a session has to understand them ("status: accepted, recorded
YYYY-MM-DD"): the reason something is the way it is gets lost faster than the code.

Format:

```
## D-NNN Title  (YYYY-MM-DD, status: proposed | accepted | rejected | superseded by D-MMM)
**Context:** why this came up (the roadmap item, the bug, the measurement).
**Decision:** what we chose (numbered points if there are several).
**Alternatives:** what else was considered, and why not (one line each). Optional, but it is what stops the
re-litigation.
**Consequences:** what it costs or constrains; what was left out and why.
**Review trigger:** an event that should cause reconsideration. Optional.
```

Plainchant Web's own decisions are not repeated here. The ones that still shape this project are summarised in [archive/plainchant-web-lineage.md](archive/plainchant-web-lineage.md); the full text is in that repository's decision log.

## D-001 Zero-build vanilla JS frontend, with vendored Prism as the one dependency  (2026-11-03, status: accepted, inherited)
**Context:** Scribe is copied from Plainchant Web, which chose a zero-build, zero-runtime-dependency frontend so that the app runs from static files in any browser, offline, and under `file://`, and so that pure logic can be tested in plain Node.
**Decision:** 1. Pure logic lives in UMD modules under `src/*.js` and is tested in Node without a DOM. 2. The app is classic `<script>` files in `src/app/*.js` sharing one global scope, loaded in order from `app.html`, each at most 500 lines, with no duplicate top-level names. 3. No framework and no npm runtime dependency. 4. The single exception is Prism 1.30.0, vendored unmodified under `src/vendor/prism/` with its licence and credited in `LICENSE`, used only to tokenize code for syntax colours. Scribe needs it for XHTML, CSS, and XML colours.
**Alternatives:** A bundler and framework (rejected: build step, size, and no offline `file://` use); CodeMirror or Monaco (rejected: megabytes of JavaScript).
**Consequences:** Every new capability, including the XML parser and the zip code, is hand-written and tested. The limits and the vendored file are documented in the lineage digest.
**Review trigger:** A need that cannot be met without a second third-party library.

## D-002 The book's files are the source of truth; edits are splices; Markdown is import only  (2026-11-03, status: accepted)
**Context:** Plainchant Web's defining idea is that a visual edit changes only the exact byte range it touches, so files never get reformatted behind the author's back. The maintainer confirmed (2026-11-03) that a Markdown-first writing app is a different product.
**Decision:** 1. A book's `.xhtml`, `.css`, and `content.opf` files are authoritative; the Studio never keeps a second model that it writes back. 2. Visual and form-based edits (metadata, spine, contents) are splices into those files, using a non-destructive XML parser with byte ranges (`P1-01`). 3. Markdown and plain text can be imported into chapters (`P5-03`) but are never the stored form of a book.
**Alternatives:** A Markdown source compiled to EPUB (rejected by the maintainer: a different product); a JSON book model serialised on export (rejected: it would reformat the author's files and lose hand edits).
**Consequences:** The XML splicer is the foundation of the project and ships first. Form edits must tolerate hand-edited OPF files, so every operation locates its target in the existing text.
**Review trigger:** A feature that cannot be expressed as a splice.

## D-003 A fresh repository, copied from Plainchant Web master, without its git history  (2026-11-03, status: accepted)
**Context:** Plainchant Scribe is a spinoff, as Plainchant Web was spun off from Plainchant. The maintainer asked for a fresh repository in `plainchant-scribe` carrying enough history to inform development without flooding the context.
**Decision:** 1. The code comes from `aedmark/plainchant-web` master at commit `4c30d7b934c771104bf3252e49807e95a5d95bdd` (2026-11-03, 37 commits, 103 passing tests, 34 recorded decisions), copied at `P0-02` without git history. 2. The history that matters is summarised in [archive/plainchant-web-lineage.md](archive/plainchant-web-lineage.md): what was built in which order, which decisions still apply, and the gotchas that cost time. 3. The upstream repository remains the place for full history.
**Alternatives:** Forking with full history (rejected: a long log mostly about features Scribe removes); a monorepo (rejected: different product, release cycle, and storage names).
**Consequences:** `git blame` stops at the copy; the lineage digest and the commit hash are the trail. Fixes to code Scribe inherited are not automatically shared in either direction.

## D-004 EPUB 3.3, reflowable first; fixed layout and the EPUB 2 fallback later  (2026-11-03, status: accepted)
**Context:** The maintainer agreed (2026-11-03) to target the current W3C EPUB 3.3 recommendation, reflowable books first.
**Decision:** 1. Books are EPUB 3.3 reflowable with XHTML content documents, a nav document, and a package document. 2. Fixed layout (`P7-01`) and the `toc.ncx` fallback (`P7-04`) are deferred. 3. Scripted and interactive content is out of scope; scripts in imported books are preserved but never run in the Reading Stage.
**Alternatives:** Fixed layout first (rejected: far fewer authors need it, and its preview needs a different Stage); EPUB 2 (rejected: superseded).
**Consequences:** The rules the code checks come from the EPUB 3.3 and EPUB Accessibility 1.1 specifications; each check cites the spec section in a comment. Reading systems still differ, so real-reader checks stay manual (see TESTING).

## D-005 Validation: built-in rules first, optional EPUBCheck  (2026-11-03, status: accepted)
**Context:** EPUBCheck is the reference validator but needs Java, so it cannot run in a browser and cannot be required. The maintainer agreed (2026-11-03).
**Decision:** 1. Scribe ships its own rule set for the common failures (`P5-04`) and shows results in the Problems tab, in the browser and the desktop app. 2. In the desktop app, when Java and an EPUBCheck jar are found, Scribe can run it and merge its messages into the same list (`P5-05`). 3. EPUBCheck is the oracle for Scribe's own tests where it is available; where it is not, that is stated in the test report instead of skipped silently.
**Alternatives:** Bundle EPUBCheck (rejected: size and a Java runtime); trust only the built-in rules (rejected: they would be graded by their author).
**Consequences:** "Passes Scribe's checks" and "passes EPUBCheck" are different claims and are reported separately.

## D-006 EPUB only: no `.mobi` or `.azw3`  (2026-11-03, status: accepted)
**Context:** Amazon accepts EPUB uploads; the older Kindle formats need separate tools.
**Decision:** Scribe exports `.epub` and does not convert to Kindle formats. The store checklist (`P6-03`) says how to upload an EPUB to Amazon.
**Consequences:** No Kindle-specific preview. Kindle behaviour is documented as a limit, not emulated.

## D-007 The Manifold and 3x documentation schemes, adopted fresh  (2026-11-03, status: accepted)
**Context:** Plainchant Web adopted both schemes and found that agent sessions stay coherent only when current state, decisions, tests, and the roadmap each have one owner. The maintainer asked for Scribe's own versions of both.
**Decision:** 1. `AGENTS.md`, `CLAUDE.md`, `ROADMAP.md`, and `docs/*` follow `the-manifold`; `tools/check_docs.py` is that repository's checker, unmodified. 2. The 3x manual is `docs/plainchant-scribe.manual.json`, built to `docs/manual.html` with `3x-documentation-scheme`'s `manual.py`, unmodified, and validated by `docs/manual.schema.json`. 3. Plainchant Web's history is not copied into the live documents (D-003).
**Consequences:** Updating either tool means replacing the file from its source repository. The manual must describe only what exists; planned features appear in the roadmap, not as manual entries, until they ship.

## D-008 A manuscript look with light and dark modes  (2026-11-03, status: accepted)
**Context:** Q-001 asked whether Scribe keeps Plainchant Web's dark studio chrome and the sister sites' paper-on-an-EGA-desk style, or gets its own look. The maintainer chose a manuscript look with a light and a dark mode (2026-11-03).
**Decision:** 1. Scribe has its own visual identity, about written pages rather than code: warm paper, ink, and serif type for the page surfaces, with restrained accents. 2. Every surface has a light and a dark variant, switchable by the user and defaulting to the system setting; the Reading Stage's own reader themes (light, sepia, dark) are separate and never change the studio chrome (`P2-02`). 3. Colours and fonts are CSS custom properties defined once, so the Stage themes, the home page, and the manual share them. 4. The inherited dark studio theme and the EGA home page are replaced, not kept as options, so there is one look to test (`P0-06`). 5. Any fonts used must be open-licensed files shipped with the app and listed in `fonts/`, as in Plainchant Web.
**Alternatives:** Keep the Plainchant Web chrome (rejected by the maintainer); offer several themes (rejected: more surface to test and nothing in the product needs it).
**Consequences:** Every inherited colour and the syntax-colour palette need a light variant with checked contrast. The Reading Stage must read as a page on a desk in both modes without looking like the book's own theme. Update 2026-11-03 (`P0-06`): implemented as EB Garamond for headings and the home page, Courier Prime for code, Inter for dense controls; `:root` is the light palette, with the dark palette written twice in CSS (once for the system setting, once for the manual choice), which a test keeps identical.

## D-009 Keep the network preview as "send to reader"  (2026-11-03, status: accepted)
**Context:** Q-002 asked whether to keep Plainchant Web's opt-in network preview. The maintainer chose to keep it as "send to reader" (2026-11-03).
**Decision:** 1. The inherited preview server (opt-in, token-gated, read-only, desktop only) stays and is renamed and adapted: it serves the book's reading view and the exported `.epub` for download, so a phone, tablet, or e-reader browser on the same network can open or fetch the book (`P5-07`). 2. Its inherited security rules apply unchanged: off until started, unguessable path token, no directory listing, stops on request or on quit. 3. Serving the `.epub` is an addition to the inherited behaviour and is recorded as such in SECURITY when built.
**Alternatives:** Drop it and rely on Export (rejected by the maintainer); a QR code (still deferred: a generator is a library-sized job under D-001).
**Consequences:** Plain HTTP on the local network, as in Plainchant Web: anyone with the link can read the book while sharing is on. It cannot help a device whose browser cannot download files.

## D-010 Test devices: Calibre, and a legacy Kindle through Calibre's conversion  (2026-11-03, status: accepted)
**Context:** Q-003 asked which reading systems the maintainer can test on. The answer (2026-11-03): Calibre and a legacy Kindle.
**Decision:** 1. Calibre (viewer and `ebook-convert`) is the first real-reader check for every release. 2. The Kindle is tested by sending a converted book, which means the result reflects Calibre's conversion and the Kindle's renderer, not Scribe's EPUB read directly. Reports must say so. 3. Scribe still does not produce Kindle formats (D-006); the test route does not change that. 4. EPUBCheck remains the validity oracle (D-005); Calibre is a rendering check, not a validator. 5. The maintainer's exact Kindle model and how books reach it are needed before Kindle results are trusted (Q-004).
**Alternatives:** Test only against EPUBCheck (rejected: validity is not rendering); buy more devices (not our call).
**Consequences:** No check on iOS, Android, Kobo, or Thorium is available to the project yet; the store checklist (`P6-03`) stays documentation and makes no compatibility claim for those. Fixes found only on the Kindle path are recorded with their conversion step.

## D-011 How XmlAst parses: character offsets, recovery, no DTD processing, limits  (2026-11-03, status: accepted)
**Context:** `P1-01` needed choices the plan left open. The maintainer chose each of them on 2026-11-03, after the agent re-read XML 1.0 (Fifth Edition), Namespaces in XML 1.0 (Third Edition), and EPUB 3.3 §3.9 and §6.1.2 on w3.org.
**Decision:** 1. Offsets are JavaScript string indices into the file's decoded text, as in `HtmlAst` and `CssAst` and the code editor; the plan's "byte ranges" (D-002, `P1-01`) means these character ranges. 2. `parse()` never throws: it reports every error it finds (up to 100) with a code, offset, line, and column, keeps going, and returns a best-effort tree marked `wellFormed: false`. The edit operations refuse a document that is not well-formed. 3. Namespaces are resolved: elements and attributes carry prefix, local name, and namespace URI, and the Namespaces in XML constraints are errors. Callers match by URI, not prefix. 4. The DOCTYPE is kept as a node and never processed. EPUB 3.3 §3.9 allows internal entity declarations, so the internal subset is scanned only for the names of internal general entities: references to them are not errors, and they are never expanded (a value keeps `&name;` as written). External entities and parameter entities are errors and are never loaded; ATTLIST defaults are ignored. 5. Limits: nesting depth 256, 16 Mi characters, 1024 attributes per element; going over one stops parsing with an error. 6. The splicer is generic (`applyEdits`, `setAttr`, `removeAttr`, `setText`, `insert`, `remove`); OPF-specific edits build on it in `P1-04`. `insert` re-parses the result and refuses markup that would make the file not well-formed. 7. Test samples are hand-written fixtures in `test/fixtures/xml/`.
**Alternatives:** UTF-8 byte offsets (rejected: an encode and decode on every splice, and the editor works in characters); stop at the first error (rejected: the code editor and Problems want every error); reject every DOCTYPE (rejected: `<!DOCTYPE html>` is normal in EPUB XHTML); expand internal entities (rejected: an attack surface, such as "billion laughs", for a rare feature); OPF-specific edits in the parser (rejected: they belong to the book model).
**Consequences:** A book that uses internally declared entities reads with `&name;` left in text and attribute values; `P1-06` decides whether to offer replacing them. ATTLIST defaults, such as a defaulted `xmlns`, are not seen. EPUB-level rules on the DOCTYPE (which external identifiers are allowed, EPUB 3.3 Appendix B) and on the encoding declaration are left to `P1-06` and `P5-04`; the parser exposes `doctype` and `xmlDecl` for them. `xml-ast.js` is not loaded by `app.html` until a feature uses it (`P1-03`).
**Review trigger:** A real book that needs entity expansion or ATTLIST defaults; a file over the limits that is not hostile.

## D-012 The new-book template, and EPUBCheck as a local test oracle  (2026-11-03, status: accepted)
**Context:** `P1-02` needed a layout, defaults, and a way to meet its acceptance test ("passes EPUBCheck") before Export exists (`P5-01`). The maintainer chose each point below on 2026-11-03, after the agent re-read EPUB 3.3 §4.2 to §4.3, §5.4 to §5.7, and §7.2 to §7.4.
**Decision:** 1. `src/book-template.js` is a pure module: `BookTemplate.create({ title, language, creator })` returns the files keyed by container path, with `mimetype` first, plus the empty folders to show. It is not wired into the app until the book model and Reading Stage can open a book (`P1-03`, `P2-01`). 2. Layout: `mimetype`, `META-INF/container.xml`, `OEBPS/content.opf`, `OEBPS/nav.xhtml`, `OEBPS/text/chapter-1.xhtml`, `OEBPS/css/book.css`, and empty `OEBPS/images/` and `OEBPS/fonts/`. 3. Defaults: title "Untitled Book" and language `en` when not given; the language goes in `dc:language` and in `xml:lang` and `lang` on every XHTML file; `dc:creator` is written only when a creator is given. The identifier is `urn:uuid:` and a random version 4 UUID from `crypto` (never `Math.random`). `dcterms:modified` is the creation time in UTC. 4. Content: a `chapter` section with a heading and one paragraph; a few neutral CSS rules with no fonts or colours. The nav has the required toc and a landmarks list pointing at the start of the text. 5. No accessibility metadata yet: claims such as "no hazards" are about content the author has not written, so `P6-01` writes them. 6. EPUBCheck is downloaded by hand into the git-ignored `.tools/` folder (5.4.0 from `w3c/epubcheck` releases, checked against the release's SHA-256). `test/epubcheck.test.js` zips the template and runs it when Java and the jar are found, checks that a deliberately broken book fails, and otherwise prints "not run" and registers no test (D-005).
**Alternatives:** A "New Book" button now (rejected: the Stage and project model still assume a web page); a flat `OEBPS/` or an `EPUB/` root (rejected: subfolders are the common layout and match the fixtures); a placeholder author (rejected: it can reach a published book); EPUBCheck only at `P5-01` (rejected: `P1-02` could not be closed).
**Consequences:** `npm test` takes about 6 seconds with EPUBCheck instead of 1. Empty folders cannot go in a zip, so they exist only in the Studio's tree until something is put in them. EPUBCheck 5.4.0 validates "using EPUB version 3.4 rules"; a landmark linking to the nav itself, which is not in the spine, is an error there (RSC-011), so the template has none. The nav's own words ("Contents", "Start of content") are English whatever the book's language.
**Review trigger:** A new EPUBCheck release that reports anything on the template; a request for localised nav labels.

## D-013 Scribe's storage and offline cache stay apart from Plainchant Web's  (2026-11-03, status: accepted)
**Context:** The maintainer asked (2026-11-03) that Scribe use its own cache and database, separate from Plainchant Web's. An audit found the names already separate since `P0-03`: IndexedDB `plainchant_scribe` (web: `plainchant_web`), `localStorage` keys `plainchant_scribe_settings` and `plainchant_scribe_emergency`, the channel `plainchant-scribe-library`, the cache `plainchant-scribe-v1`, and the bundle id `io.plainchant.scribe`. Both desktop servers bind random ports. But the inherited service worker deleted every cache on its origin that was not its own and answered from `caches.match()`, which searches all of them. Both projects' docs also served the app on port 8080. Run on one origin, Scribe would delete Web's offline cache and could serve Web's cached files, and the two would fight over one service worker scope.
**Decision:** 1. The service worker deletes only caches whose names start with `plainchant-scribe-`, and reads only from its own cache. 2. Scribe's browser dev server uses port 8081 (`npm run serve`), so it never shares an origin, and with it storage quota and service worker scope, with Plainchant Web on 8080. 3. Structure tests guard both: `sw.js` runs against a fake cache store that holds another app's cache, and the serve script must use 8081.
**Alternatives:** A different service worker scope, such as a subfolder (rejected: the app lives at the site root); unregistering the other app's worker (rejected: one app must not manage another's).
**Consequences:** Anyone with bookmarks to `localhost:8080/app.html` for Scribe starts with empty storage on 8081. Plainchant Web's own service worker still deletes other caches on its origin; that matters only if the two apps share an origin again, and it is a fix for that repository. Desktop isolation rests on the separate bundle identifiers, which Tauri uses for each app's WebView data folder; this was not checked in a real window.

## D-014 How Book reads a package document, and which problems it reports  (2026-11-03, status: accepted)
**Context:** `P1-03` needed choices about finding the OPF, the model's shape, and where its checks stop and `P5-04`'s begin. The maintainer chose each point below on 2026-11-03, after the agent re-read EPUB 3.3 §4.2, §5.3 to §5.9, and Appendix D.6.
**Decision:** 1. `Book.read(files, { assets })` finds the package document only through `META-INF/container.xml`, using the first rootfile with media type `application/oebps-package+xml`. A missing or broken container, a missing OPF, or an OPF that is not well-formed gives no model, only problems. 2. The model holds values and the XmlAst node of every metadata entry, item, and itemref (and, not enumerable, the OPF's parse), so `P1-04` can splice exactly them. It is a fresh read every time and never written back (D-002). 3. Refining `meta` and `link` elements are attached to their subject's `refinements` and also kept in `metadata.metas` in document order. 4. Problems are `{ severity, code, message, path, start, end, line }`: errors for EPUB 3.3 MUSTs, warnings for SHOULDs, info for legacy notes, each message citing its section. 5. Only package rules are checked: what can be known from the OPF and the file list. Cross-file content checks (links, anchors, alt text, headings, nav links into the spine) stay in `P5-04`. 6. EPUB 2 leftovers (`<meta name="cover">`, `<guide>`, `spine toc`) are read into `model.legacy` and reported as info; `<meta name="cover">` names the cover only when no item has `cover-image`. 7. Neither `xml-ast.js` nor `book.js` is loaded by `app.html` until a screen uses them.
**Alternatives:** Search for an `.opf` when the container is broken (rejected: the container is required, and guessing hides a broken book); plain values only (rejected: `P1-04` would have to find its targets again); errors only (rejected: the Problems tab wants SHOULDs and legacy notes too); refinements as a flat list only (rejected: every caller would match `refines` itself).
**Consequences:** A book with a damaged container shows nothing in the Book panel until the container is fixed, though the code editor still opens every file. EPUBCheck 5.4.0 does not report an `mimetype` item in the manifest, which EPUB 3.3 §4.2.2 forbids; Scribe reports it as an error, so here "passes Scribe's checks" is stricter than "passes EPUBCheck" (D-005).
**Review trigger:** Real imported books whose containers are broken often enough that the strict rule gets in the way.

## D-015 How OPF edits are made: splices from a fresh model, refusing breakage only  (2026-11-04, status: accepted)
**Context:** `P1-04` needed choices about where edit operations live, what they return, what "rename" means, how removals cascade, who updates `dcterms:modified`, which metadata operations exist, when an op refuses, and how the spine is reordered. The maintainer chose each point below on 2026-11-04. The rules cited are those re-read for D-014 (EPUB 3.3 §4.2, §5.3 to §5.9), plus XML 1.0 §3.3.1 for ids; RFC 6838 §4.2 for media types is cited from memory.
**Decision:** 1. A separate UMD module, `src/opf-edit.js` (`OpfEdit`), not part of `book.js`. 2. Every op takes a fresh `Book.read` model and returns XmlAst edits `[{ start, end, text }]`; the caller applies them and reads the book again before the next op. 3. Rename covers both: `renameItem` changes an item's id and every OPF reference to it (itemrefs, fallback, media-overlay, spine `toc`, refines, the EPUB 2 cover meta); `setItemPath` changes only the href. Moving the file and fixing links in content documents are left to the Explorer and nav work. 4. `removeItem` also removes the item's itemrefs, the metas that refine it, the spine's `toc` attribute and the EPUB 2 cover meta that name it, and refuses the nav document and an item another item uses as its fallback or media overlay. 5. No op changes `dcterms:modified` except `touchModified(model, now)`, which Export or the save path calls once. 6. Metadata ops are generic: any DCMES element (`addDc`, `setValue`, `removeMetadata`), any book-level meta property (`setMeta`, `removeMeta`), and refinements (`setRefinement`); `setTitle` and `setLanguage` are thin wrappers. 7. Ops throw an Error with a `.code` for structural breakage: an invalid or repeated id, an unknown idref, a repeated spine entry, a bad media type, a path outside the book or reserved for the container, a repeated href, or markup that is not well-formed. They allow edits that leave a package rule unmet (removing the last title, listing a file not yet added); `Book.read` reports those. 8. The spine is reordered by `moveItemref(model, idref, toIndex)` and `setSpineOrder(model, idrefs)`; each itemref moves with the text before it back to the previous itemref, so comments travel with it, and one edit replaces only the itemref run.
**Alternatives:** Ops inside `book.js` (rejected: reading and writing stay apart); ops returning new text (rejected: chaining re-parses anyway, and edit lists suit undo and batching); rename meaning only the id, or also moving the file (rejected: the first leaves hrefs without an op, the second reaches into content documents); cascading every reference or refusing any reference on removal (rejected: clearing a fallback silently changes another item, and refusing makes the caller remove itemrefs first); every op touching `dcterms:modified` (rejected: two places change per edit and tests stop being deterministic); refusing any edit that adds a `Book.read` error (rejected: it blocks intermediate states such as replacing the only title).
**Consequences:** Two ops on one model cannot always be combined; a caller that wants one undo step for several ops applies them one at a time and snapshots once. A book whose OPF is not well-formed cannot be edited through `OpfEdit`, only in the code editor. A path with spaces is accepted and written as `%20`, which EPUBCheck warns about (PKG-010, `P5-04`).
**Review trigger:** The Book panel (`P3-01`) needs an op that these cannot express, or applying ops one at a time proves too slow on a large OPF.

## D-016 How the nav document is read and edited, and where Scribe follows EPUBCheck over §7  (2026-11-04, status: accepted)
**Context:** `P1-05` needed choices about the nav checks, how the table of contents is edited, what removing an entry does, how new navs are written, and the module's shape. The maintainer chose each point below on 2026-11-04, after the agent re-read EPUB 3.3 §7 on w3.org. A by-hand EPUBCheck comparison then showed four places where EPUBCheck 5.4.0 is stricter than §7, and the maintainer chose to follow EPUBCheck.
**Decision:** 1. One UMD module, `src/nav.js` (`Nav`), reads and edits. `Nav.read(files, bookModel)` finds the nav through the Book model and returns `{ nav, problems }` in Book's problem shape. 2. It checks the §7 rules (content model, one toc, at most one landmarks and page list, landmark `epub:type` and repeats, toc order as a warning, flat landmarks and page list as a warning). It also checks that toc, landmarks, and page-list links reach a spine document (RSC-011), which moves from `P5-04` to here; fragments are still `P5-04`'s. 3. Edits follow D-015: a fresh model in, XmlAst edits out, breakage refused with a coded error, rule gaps allowed. They are entry splices (`setLabel`, `setHref`, `addEntry`, `removeEntry`) plus `replaceList(nav, navObj, tree)`, which rewrites one nav's top `<ol>` in the file's indentation and line ends; `toTree` gives the tree to edit, with labels as text. 4. `removeEntry` removes the subtree, and a sublist it empties. 5. New landmarks and page-list navs get `hidden=""` (§7.5) and go after the last typed nav; the toc is never hidden or removed by Scribe. 6. Where EPUBCheck 5.4.0 rejects what §7 allows, Scribe reports an error that names EPUBCheck as its source, so a book Scribe passes also passes the oracle (D-005). The cases are a nav link whose only label is an image's alt text, an other typed nav without a heading, a link to a document reached only through a spine item's fallback, and an internal link in an other typed nav that is not in the spine. A toc, landmarks, or page-list link with no href is a warning, as EPUBCheck accepts it.
**Alternatives:** Nav rules only, with link targets left to `P5-04` (rejected: the nav is the one file whose links must reach the spine, and EPUBCheck fails books on it); verbatim moves of hand-formatted entries (rejected for now: harder, and `P3-04` needs a whole-list writer anyway); promoting children on removal (rejected: `replaceList` does that); visible new navs (rejected: landmarks and page lists are for reading systems); following §7 and only warning for EPUBCheck's extra rules (rejected: books would pass Scribe and fail the oracle).
**Consequences:** `replaceList` drops inline markup in labels and hand formatting inside the list it rewrites. Some books that conform to §7 get errors in Scribe, each saying EPUBCheck is the reason. The four EPUBCheck rules must be checked again when EPUBCheck changes.
**Review trigger:** A new EPUBCheck release changes one of the four rules, or authors need inline markup kept when the toc is reordered.

## D-017 How XHTML is checked, how HTML entities are fixed, and how pasted HTML is cleaned  (2026-11-04, status: accepted)
**Context:** `P1-06` needed choices about the checks a chapter gets, which HTML entity names Scribe knows, what replaces them, how pasted HTML is parsed, and how much the paste is cleaned. The maintainer chose each point below on 2026-11-04, after the agent re-read EPUB 3.3 §3.9, §6.1, and Appendix B on w3.org.
**Decision:** 1. `src/xhtml.js` (`Xhtml`) checks XML well-formedness, the §3.9 XML rules, the basic document shape (`html` holding `head` with a `title`, then `body`), XInclude, `epub:type` on metadata content (§6.1.3.1), and warns about `<base>` and `<rp>` (§6.1.4.3). HTML's content model, alt text, and headings stay in `P5-04`. 2. Scribe knows the 252 HTML 4.01 entity names (the table was generated from Python's `html.entities.name2codepoint`, which is that set). Other undeclared names stay plain XML errors. 3. `fixEntities` writes the character itself, except characters that cannot be seen in an editor (no-break and other special spaces, soft hyphen, zero-width and direction marks, U+FEFF), which become decimal references. The normaliser writes text the same way. 4. The browser's own HTML parser (`DOMParser`) reads a paste, and a pure function walks the DOM-like tree, so implied end tags behave as in a browser and Node tests use hand-built trees. 5. The paste keeps semantic elements and a short list of attributes (`id`, `lang`, `dir`, `title`, `role`, `aria-*`, and per-element ones such as `href`, `src`, `alt`, `colspan`). It drops styles, classes, other attributes, scripts and other active or form content, Word's Office elements and drawn list numbers, Docs' wrapper, layout wrappers, and paragraphs left empty. 6. Inline bold and italic styles become `<b>` and `<i>`; `<strong>` and `<em>` are kept as they are. 7. Images are kept with their `src` and `alt` and returned in a list, so the app can offer to import them. 8. Following D-016's rule, where EPUBCheck 5.4.0 differs, Scribe follows it: UTF-8 only, since HTML requires it and EPUBCheck reports HTM-058 for UTF-16; an empty `<title>` is an error; a missing `<title>` and a DOCTYPE name other than `html` are warnings.
**Alternatives:** HTML content-model checks now (rejected: large, and EPUBCheck already does them); the full WHATWG list of 2,231 names (rejected: a CC BY 4.0 notice in the protected LICENSE for little gain); always numeric or always the character (rejected: unreadable code, or invisible characters); an own HTML parser or the inherited HtmlAst (rejected: they would differ from browsers on messy pastes); keeping classes, or fixing syntax only (rejected: pasted presentation fights the book's own CSS); `<strong>`/`<em>` for styled text (rejected: it claims emphasis the author may not mean); dropping or replacing images (rejected: the author loses them silently).
**Consequences:** The normaliser can only run where a `DOMParser` exists (the browser and the Tauri webview); Node tests cover the walk, not the parse. A paste loses its fonts, colours, and spacing on purpose. Word's hand-made numbered lists come through as plain paragraphs.
**Review trigger:** Authors often need class names kept, or need Word's lists turned into real lists.

## D-018 How a book opens in the Studio and how the Stage shows a chapter  (2026-11-04, status: accepted)
**Context:** The maintainer found on 2026-11-04 that New still made a Plainchant Web page, and asked that opening books be part of `P2-01`. The Studio's project model and Stage were built for one HTML page with `index.html`, `styles.css`, and `script.js`. The maintainer chose each point below on 2026-11-04.
**Decision:** 1. The Stage loads a chapter as `application/xhtml+xml` from a Blob URL, so the browser parses it as a reading system does, and shows an error page when it is not well-formed. Stage selection and inline editing are off for chapters until `P2-06`; the code editor, Inspector panes, and Explorer still work. 2. Load Example Book, and the first run with an empty library, open a three-chapter guide to Scribe written for it (`src/example-book.js`), made with `BookTemplate`, `OpfEdit`, and `Nav`. 3. Projects saved before this change keep opening and rendering as web pages. 4. New makes "Untitled Book" at once, with no dialog; details are edited later (`P3-01`). 5. A project is a book when it has `META-INF/container.xml`. Then `Project` adds no web-page default files, saves its tree so empty folders survive a reload, and takes its title from the OPF's first `dc:title`. 6. The Stage shows the XHTML file last opened in the editor, else the first chapter in the spine. 7. The Stage gets a copy of the chapter with stylesheets inlined, asset URLs pointed at Blob URLs, and scripts, event-handler attributes, and `javascript:` URLs removed; the book's files are never changed. Links to other files are stopped in the frame until `P2-05`.
**Alternatives:** Render chapters as HTML through the existing `srcdoc` path with the Design bridge (rejected: the HTML parser repairs what a reader would reject, and HtmlAst edits could write HTML-only syntax into XHTML); a public-domain excerpt, or no example (rejected: an original guide doubles as a test book); a notice on old projects (rejected: not needed while they still work); a details dialog on New (rejected: more markup now, and the Book panel will edit them).
**Consequences:** Editing a chapter means the code editor until `P2-06`. Books and old web projects follow two paths through the Studio, told apart by one file. The Stage iframe's sandbox (`allow-scripts allow-same-origin`, inherited) does not isolate scripts, so removing them from the copy is what keeps book content from running.
**Review trigger:** `P2-06` brings editing to chapters, or the Tauri webview handles Blob URLs differently.

## D-019 The offline cache is network first  (2026-11-04, status: accepted)
**Context:** `sw.js` was cache-first under a fixed name (`plainchant-scribe-v1`), so an installed browser kept serving old app files until `sw.js` itself changed. Inherited from Plainchant Web, noted as an open weakness in the lineage digest, and seen in `P2-01` when an edit to `app.html` did not show. The maintainer chose network first on 2026-11-04.
**Decision:** Online, every same-origin GET goes to the network with `cache: 'no-cache'` (revalidated past the HTTP cache), and an `ok` response replaces the stored copy, keyed by URL without query or fragment. Offline, or when the network fails, the stored copy answers, or a network error if there is none. Install stores every app file with `cache: 'reload'`. Other origins and non-GET requests are not handled. The cache name stays `plainchant-scribe-v1`, and only that cache is read or written (D-013).
**Alternatives:** Cache first, refreshed in the background (rejected: every update shows one load late); cache first with a hash of every app file in `sw.js`, enforced by a test (rejected: one more step on every commit that touches the app).
**Consequences:** Every load online makes a round trip per file, which is a revalidation and usually a 304 from the server. A file that fails on the network is served from the cache only if the request fails outright; a 404 or 500 passes through.
**Review trigger:** Loads become slow on poor connections, or the app gains files the user should keep using offline while the server is changing them.

## D-020 Reader settings on the Stage: what they override, where they live, and their defaults  (2026-11-04, status: accepted)
**Context:** `P2-02` needed choices about how strongly reader settings override the book's CSS, where the controls go, whether they are remembered, and what the Stage shows by default. The maintainer chose each point below on 2026-11-04.
**Decision:** 1. Like a typical reading system: text size scales the book's own root font size (read after load, so em and rem follow and px does not); margins and the theme's page and text colours are forced on `html` and `body` with `!important`; colours the book sets on particular elements stay, and the theme's link colour yields to the book's. 2. A Reader button on the Stage bar, shown only for books, opens a panel with text size, margins, theme, and a reset. 3. The choices are saved with the Studio's settings (`readerSize`, `readerMargins`, `readerTheme`) and apply to every book; they are never written into a book. 4. The defaults are 100%, normal margins (1em 1.5em), and light, so the Stage looks like a reader out of the box rather than the book's bare CSS. Theme colours must reach 4.5:1 for text and links (tested).
**Alternatives:** Forcing the theme colour and size on every element (rejected: it hides how the book's own styles behave); never using `!important` (rejected: a book's `body { margin: 0 }` would beat the margins); setting `html { font-size }` in CSS (rejected: it would override a book's `62.5%` root and break its rem sizes); buttons always on the bar, or the controls in Settings (rejected: a crowded bar, or slow to try sizes); per-book or unsaved settings (rejected: reading apps keep one set of preferences); the book as written by default (rejected: a reader never shows text against the frame edge).
**Consequences:** The Stage never shows the bare book CSS; checking that needs the code. Scaling on load means a brief reflow when the size is not 100%. Paged mode and device presets (`P2-03`, `P2-04`) build on the same Stage copy.
**Review trigger:** Authors need to see the book with no reader overrides, or a target reader is found to override differently.

## D-021 Paged mode on the Stage: columns, the page count, and how pages turn  (2026-11-04, status: accepted)
**Context:** `P2-03` needed choices about the default layout, what the page indicator counts, two-page spreads, and how pages turn. The maintainer chose each point below on 2026-11-04.
**Decision:** 1. Paged is the default layout and Scroll the alternative, chosen in the Reader panel and saved with the other reader settings (`readerMode`). 2. Pages are counted within the open chapter. 3. One page at a time at every width; spreads may come with the device presets (`P2-04`). 4. Pages turn with ‹ and › on the Stage bar and with Left, Right, Page Up, and Page Down when the Stage has focus; clicking the page edges does not turn pages, so it cannot clash with Stage editing (`P2-06`). How it works: CSS columns on `body`, each column's width plus gap exactly one viewport, `html` not scrollable by the user; a turn sets `scrollLeft` to a whole number of viewport widths. A 1px marker in the Stage copy makes the scroll width whole pages, an in-chapter link turns to its target's page, and other scrolls snap to a page.
**Alternatives:** Scroll by default (rejected: the Stage should look like the target reader); a page count for the whole book (rejected: every chapter laid out on every change); spreads on wide Stages (rejected for now: simpler, and the device presets will choose); edge clicks (rejected: they clash with clicking text once Stage editing returns).
**Consequences:** Page numbers depend on the Stage's size, the reader settings, and the fonts, as on a device. Mouse-wheel and touch paging are not handled.
**Review trigger:** `P2-04` adds spreads, or a whole-book page count is needed for the page list (`P6-02`).

## D-022 Device presets on the Stage  (2026-11-04, status: accepted)
**Context:** `P2-04` needed choices about what replaces the inherited viewport switch for books, the preset sizes, what e-ink changes, and orientation. The maintainer chose each point below on 2026-11-04.
**Decision:** 1. For books, Fit, Phone, E-ink, and Tablet replace the 100%/768px/375px switch; web-page projects keep it. 2. Portrait sizes in CSS px: Phone 390 × 844, E-ink 6" 600 × 800, Tablet 820 × 1180. The frame is drawn at that size and scaled down, never up, to fit the Stage. 3. E-ink is greyscale (a filter on the frame, so it covers the page colour too) with CSS animations and transitions off; the reader theme still applies. 4. A rotate button swaps width and height, still one page at a time (D-021). The device and orientation are saved with the reader settings.
**Alternatives:** A custom size as well (rejected for now: the presets cover the targets); a smaller phone and a 7-inch e-ink (rejected: the chosen sizes are the common cases); an e-ink paper look (rejected: it would override the chosen theme); a spread in landscape tablet, or portrait only (rejected: one page keeps paging simple, and rotation is cheap).
**Consequences:** The sizes are approximate: each reading app adds its own margins and chrome. A scaled-down device frame shows smaller text than the device would.
**Review trigger:** The maintainer's devices (D-010, Q-004) show page breaks the presets do not match.
